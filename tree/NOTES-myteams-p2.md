## Routes (all in `_worker.js`, all responses `Cache-Control: no-store`)
- `GET /api/auth/google/start?r=/path` - rate limit 10/hour per visitor; makes state (32 random bytes), PKCE verifier (S256) and nonce; stores them in a signed `__Host-kt_oauth` cookie (10 min); 302 to Google (`prompt=select_account`, scope `openid email profile`, exact redirect_uri). `r` must be a plain same-site path or it becomes `/`.
- `GET /api/auth/google/callback` - state must equal the signed cookie (login-CSRF / replay), cookie age <= 10 min; code exchanged server to server at `https://oauth2.googleapis.com/token` (HTTPS, client secret never leaves the Worker) with the PKCE verifier; ID token claims checked (iss, aud, exp, nonce, email_verified, sub); user upserted by Google `sub`; `__Host-kt_session` set; 302 back with `?signin=ok|error|cancelled` (account.js removes the parameter).
- `GET /api/auth/session` - `{configured, signedIn, email, name, initial, cap}`; works (as `configured:false`) with no secrets.
- `POST /api/auth/logout` - Origin check; clears the cookie.
- `GET /api/teams`, `PUT /api/teams` `{teams:[slug], lead:{slug:p|c|w|b}}` - PUT: Origin must equal `https://kicktipmedia.com`, JSON only, <= 8 KB, **cap 50 server side** (409), every slug must be in the real team list, no duplicates, lead keys must be in the list, any unknown field or malformed body is rejected (never repaired), 60 saves/hour per user (429), whole list replaced in one D1 batch.
- `POST /api/account/delete` - Origin check, 3/day, deletes the user and every saved team, clears the cookie.
- Session cookie: `__Host-kt_session` (Secure, HttpOnly, SameSite=Lax, Path=/, no Domain), value = `v1.<payload>.<HMAC-SHA256 with SESSION_SECRET>`, 30 days, revocable per user (`users.sess_ver`). Unsafe methods require `Origin: https://kicktipmedia.com`; GETs refuse `Sec-Fetch-Site: cross-site`.
- Rate-limit key = keyed hash of the visitor address (the address itself is never stored); counters live in D1 `rate_limits` and are swept.
- The anonymous 10-team cap is client side (phase 1, `site_config.MYTEAMS_CAP_LOCAL`); the 50 cap is enforced by the Worker.

## Data stored (D1)
`users`: id, google_sub, email, display_name (optional), created_at, sess_ver. `saved_teams`: user_id, slug, lead code, position, added_at. `rate_limits`: keyed hash, window, count, expiry. `email_tokens`: phase 3 only (empty now). Nothing else. No analytics, no IP address, no user agent.

## Check of _headers / CSP
`_headers` is unchanged: `script-src 'self'`, `style-src 'self'`, `connect-src 'self'`, `worker-src 'self'`, `form-action 'none'`. Nothing was loosened. Why Google still works: sign-in is a full-page navigation (a plain link to our own `/api/auth/google/start`, which 302s to Google and back); CSP `form-action` only governs forms, and navigations are not governed by `connect-src`/`default-src`. All fetches from account.js are same-origin (`/api/...`). The Google "G" logo is inline SVG (no `img-src` change). The API responses carry their own strict CSP (`default-src 'none'`).

## Phase 3 (email-link sign-in) - NOT built; structured to drop in
CEO approved it after Google sign-in. **Link lifetime: 15 minutes, single use (CEO confirmed; Creative recommended it).** One constant, `EMAIL_LINK_TTL_SECONDS = 900` in `src/site_config.py`; build.py injects it into `_worker.js` (where `expires_at = created_at + EMAIL_LINK_TTL_SECONDS` will use it) and into the /privacy/ wording ("expires after 15 minutes", shown only when `PHASE3_EMAIL_LINK` is on). The 14 days in the first draft migration was wrong for a sign-in link and is gone; the only 14-day value left is the sheet's "Not now" snooze. Prepared now: migration `0003_email_tokens.sql` (token_hash PK = SHA-256 of the token, email, created_at, expires_at = created_at + `EMAIL_LINK_TTL_SECONDS`, used_at), and `finishSignIn(env, user, path, now, cookies)` in the Worker is the single place any provider ends (session cookie + redirect). Design:
- `POST /api/auth/email/start {email}`: Origin check; rate limit 10/hour per visitor (same `hit()` helper, new kind) and per address; always answers the same generic 200 (no account enumeration); creates 32 random bytes, stores only the hash, sends `https://kicktipmedia.com/signin/confirm/#t=<token>` through the email provider (called from the Worker with `EMAIL_API_KEY`, from-address on kicktipmedia.com; provider/DNS per /workspace/hub/kicktip-email/EMAIL-SENDER-RESEARCH.md).
- The link opens a static page that shows a "Sign in" BUTTON; the token sits in the URL fragment (never sent to a server, so mail scanners that prefetch the link cannot consume it). The button does `POST /api/auth/email/verify {token}` which atomically does `UPDATE email_tokens SET used_at=? WHERE token_hash=? AND used_at IS NULL AND expires_at>?`; one changed row = valid; then find-or-create the user by email (needs migration 0004: `users.google_sub` nullable + unique index on lower(email), linking an existing Google account with the same verified email) and call `finishSignIn`.
- Privacy impact to decide with Creative: the address is passed to the email provider (a processor); the sheet must then say so, and the exact "No third-party requests" line stays true for the browser (the send is server side) but the storage line needs "your email is sent once to our email provider to deliver the link". Email-link UI is NOT in this build (no field, no text).
